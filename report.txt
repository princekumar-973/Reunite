1. INTRODUCTION
================================================================================

1.1 PURPOSE
The purpose of this Software Requirements Specification (SRS) is to provide a 
complete, unambiguous, and authoritative description of the "Reunite" platform 
(Smart Lost & Found Management System). This document formally captures both 
the functional and non-functional requirements governing the design, construction, 
testing, deployment, and verification of Reunite.

The intended audience includes:
- Academic Evaluators, Course Instructors, and Project Mentors.
- Software Architects, Full-Stack Engineers, and Database Administrators.
- Quality Assurance (QA) and Security Engineers conducting testing.
- End Users and Administrative Stakeholders reviewing system deliverables.

1.2 SCOPE
"Reunite" is a decentralized, secure, and modern web application engineered to 
solve the chaos of misplaced personal belongings across university campuses, 
residential communities, public transit networks, and commercial complexes.

What Reunite WILL DO:
1. Public Browsing Gateway: Enable any student, faculty member, or visitor to 
   instantly access the platform home page, search the registry, filter items by 
   category, date, status, and campus zone without requiring upfront login.
2. Action-Gated User Authentication: Enforce strict user registration and JWT 
   login when any user attempts to execute actions (e.g., reporting a misplaced 
   item, claiming a found item, updating custody status).
3. Geo-Referenced & Multi-Media Reporting: Facilitate item submission with live 
   device camera photo capture, file uploads, GPS coordinates, and detailed 
   metadata (brand, color, campus area).
4. Dual-Factor Verification Engine: Protect found property from fraudulent 
   claims through custom secret challenge questions (e.g., "What is the lock 
   screen wallpaper?") and proof document descriptions.
5. Item Lifecycle Tracking: Full state transitions (OPEN -> CLAIMED -> RESOLVED).
6. Cross-Platform Responsive Interface: Fully accessible via desktop and mobile.

What Reunite WILL NOT DO:
1. Physical Courier Logistics: Reunite facilitates virtual identification and 
   custody verification; physical transfer occurs via designated campus zones.
2. Monetary Payouts for Lost Items: Reunite prohibits commercial ransom or 
   monetary reward demands to maintain community trust and integrity.

2. GENERAL DESCRIPTION
================================================================================

2.1 PRODUCT PERSPECTIVE
Reunite operates as a distributed, service-oriented multi-tier web application:
- Client Tier (Frontend)   : React 19 + TypeScript + Vite + Tailwind CSS v4 SPA.
- Server Tier (Backend API): Django REST Framework with SimpleJWT middleware.
- Data Tier (Database)     : MongoDB Atlas (Cloud NoSQL) / MongoDB Community Server.
- Cloud Hosting Tier       : Vercel Serverless Edge Cloud hosting.

+-----------------------------------------------------------------------------+
| CLIENT LAYER (React 19 + Vite SPA @ https://reunite-xi.vercel.app)          |
| - Hero Analytics  - Catalog Search  - Live Camera Capture  - Claim Dashboard|
+-----------------------------------------------------------------------------+
                                       | HTTPS / JSON (REST API)
                                       v
+-----------------------------------------------------------------------------+
| BACKEND API LAYER (Django + DRF @ https://reunite-qcso.vercel.app)          |
| - JWT Auth Gate   - Item Controller - Claim Validator  - CORS Middleware    |
+-----------------------------------------------------------------------------+
                                       | Mongo Wire Protocol
                                       v
+-----------------------------------------------------------------------------+
| DATABASE LAYER (MongoDB Atlas Cloud Cluster / Local 27017)                  |
| - lostandfound.users  - lostandfound.items  - lostandfound.claims           |
+-----------------------------------------------------------------------------+

2.2 PRODUCT FUNCTIONS
1. User Identity & Profile Lifecycle: Secure sign up, credential encryption, 
   session management via short-lived JWT access tokens and long-lived refresh tokens.
2. Dynamic Search & Filtration: Filter directory items by classification (LOST, 
   FOUND), category, campus area, resolution status, and sub-second full-text queries.
3. Item Registration & Geolocation: Register misplaced or recovered belongings 
   with photos, location descriptions, and GPS latitude/longitude.
4. Ownership Proof & Claim Adjudication: Found item reporters evaluate claims 
   submitted by claimants, reviewing answers to secret questions and proof logs.
5. Real-Time Telemetry: Live aggregate metrics counting reported items, active 
   cases, and successfully reunited items.

2.3 USER CHARACTERISTICS
1. Casual Visitor (Public Guest): Has not logged in. Can freely browse the directory, 
   view item listings, and run search queries. Prompted to authenticate when claiming 
   or reporting.
2. Registered Claimant: An individual who has misplaced a possession. Can submit 
   claims, submit ownership evidence, and track claim resolution.
3. Registered Finder (Custodian): An individual who discovered a lost belonging. 
   Can upload items, set secret verification questions, review claims, and mark 
   items as REUNITED.
4. System Administrator: Can manage database records, delete flagged listings, 
   and oversee community compliance.

2.4 GENERAL CONSTRAINTS
- Platform must run across modern standard browsers (Chrome, Edge, Firefox, Safari).
- Backend must comply with Vercel serverless execution limits (Python execution <= 15MB).
- Database must use MongoDB NoSQL with native BSON indexing.
- Secret credentials, API keys, and database passwords must never be exposed to clients.

2.5 ASSUMPTIONS AND DEPENDENCIES
- Client devices have internet connectivity and standard JavaScript enabled.
- For camera uploads and geolocation, the user grants camera and location permissions.
- MongoDB Atlas cluster is accessible via TLS port 27017 from cloud serverless runners.

3.1.3 SOFTWARE INTERFACES

- Runtime          : Node.js 18+ (Frontend) and Python 3.10+ / 3.11 (Backend).
- Database Engine  : MongoDB 6.0+ via PyMongo and `django-mongodb-backend`.
- Web Server       : Vercel Serverless Function Engine / WSGI development server.

3.1.4 COMMUNICATIONS INTERFACES
- Protocol         : HTTPS (TLS 1.3) for all client-to-server and server-to-db traffic.
- Serialization    : JSON (JavaScript Object Notation) for all API payloads.
- Security Headers : CORS (Cross-Origin Resource Sharing) with credentials, CSRF protection.

3.2 FUNCTIONAL REQUIREMENTS

3.2.1 FEATURE 1: USER REGISTRATION, LOGIN & JWT AUTHENTICATION
3.2.1.1 Introduction
Allows users to securely create an account, authenticate, receive JWT tokens, 
and manage authenticated sessions.
3.2.1.2 Inputs
- Registration: `username` (string), `email` (valid email), `password` (min 6 chars), 
  `first_name` (string), `last_name` (string), `phone` (string, optional).
- Login: `username` (string), `password` (string).
3.2.1.3 Processing
- Passwords are encrypted using Django's PBKDF2 algorithm with SHA-256 hash.
- Upon valid credentials, SimpleJWT issues an `access` token (60 min expiry) 
  and a `refresh` token (7 days expiry).
3.2.1.4 Outputs
- HTTP 201 Created on registration with user profile and token pair.
- HTTP 200 OK on login with access and refresh tokens.
3.2.1.5 Error Handling
- HTTP 400 Bad Request for duplicate usernames or malformed email addresses.
- HTTP 401 Unauthorized for incorrect passwords or non-existent user accounts.

3.2.2 FEATURE 2: PUBLIC BROWSING & REAL-TIME SMART FILTERING
3.2.2.1 Introduction
Enables any visitor landing on the home page to explore lost and found items 
immediately without upfront login friction.
3.2.2.2 Inputs
- Query parameters: `item_type` (LOST, FOUND), `category` (ELECTRONICS, KEYS, etc.), 
  `status` (ALL, OPEN, RESOLVED), `q` (free-text search keyword).
3.2.2.3 Processing
- Backend executes multi-field queries across title, description, brand, and location.
- Results are sorted chronologically by reporting timestamp.
3.2.2.4 Outputs
- Array of matching item objects containing title, photo URL, date, category, status.
3.2.2.5 Error Handling
- If no items match, the UI renders an intuitive empty state with "Reset Filters" action.

3.2.3 FEATURE 3: LOST & FOUND ITEM REPORTING WITH GPS & MEDIA
3.2.3.1 Introduction
Authenticated users can submit lost or found belongings with rich descriptive data, 
GPS coordinates, and item imagery.
3.2.3.2 Inputs
- `title`, `item_type` (LOST/FOUND), `category`, `description`, `location`, 
  `campus_area`, `date_lost_or_found`, `brand`, `primary_color`, `image_url` / photo, 
  `contact_email`, `contact_phone`, `secret_verification_question`.
3.2.3.3 Processing
- If the user is unauthenticated, the system intercepts the click and displays the 
  Registration / Login modal with the prompt: "Please register or log in to report an item."
- Upon successful authentication, the pending submission proceeds and records to MongoDB.
3.2.3.4 Outputs
- HTTP 201 Created returning the stored item object with unique MongoDB ObjectId.
3.2.3.5 Error Handling
- HTTP 400 Bad Request if mandatory fields (title, category, description) are missing.

3.2.4 FEATURE 4: CLAIM VERIFICATION & SECRET QUESTION CHALLENGE
3.2.4.1 Introduction
Prevents wrongful possession handover by requiring claimants to answer secret 
questions established by the finder.
3.2.4.2 Inputs
- `item_id`, `message` (claim justification), `proof_description` (unique identifying marks), 
  `secret_question_answer` (answer to verification challenge), `contact_phone`.
3.2.4.3 Processing
- Unauthenticated claimants are required to register or sign in before submitting proof.
- Claim is linked to the claimant's account and the finder's item registry.
3.2.4.4 Outputs
- HTTP 201 Created. The claim status is initialized to `PENDING`.
3.2.4.5 Error Handling
- HTTP 403 Forbidden if a user attempts to claim an item they themselves reported.

3.2.5 FEATURE 5: CLAIMS & ITEM MANAGEMENT WORKSPACE
3.2.5.1 Introduction
A dedicated dashboard for users to review incoming claims, verify evidence, 
approve or reject claims, and mark recovered items as `RESOLVED`.
3.2.5.2 Inputs
- `claim_id`, `status` (APPROVED / REJECTED), `owner_notes` (feedback to claimant).
3.2.5.3 Processing
- Finder approves legitimate claimant; system automatically transitions the item 
  status from `OPEN` to `CLAIMED` or `RESOLVED`.
3.2.5.4 Outputs
- HTTP 200 OK with updated claim and item state.

3.2.6 FEATURE 6: PLATFORM HEALTH & ANALYTICAL METRICS
3.2.6.1 Introduction
Automated system monitoring endpoint exposing database connectivity and metrics.
3.2.6.2 Inputs: None (HTTP GET `/api/health/` and `/api/v1/items/stats/`).
3.2.6.3 Outputs: JSON payload with service health, MongoDB connectivity, item counts.

--------------------------------------------------------------------------------
3.5 NON-FUNCTIONAL REQUIREMENTS

3.5.1 PERFORMANCE
- 95% of database read queries (directory browsing, item details) shall return within 
  <= 400 milliseconds under standard network conditions.
- Frontend static assets shall bundle under 400 KB gzipped via Vite code-splitting.

3.5.2 RELIABILITY
- Mean Time Between Failures (MTBF) shall exceed 720 hours (30 continuous days).
- System shall maintain data consistency across MongoDB write operations.

3.5.3 AVAILABILITY
- The web application and backend API shall achieve >= 99.5% service uptime on Vercel.
- Database automatic failover handled via MongoDB Atlas multi-region replicas.

3.5.4 SECURITY
- Passwords hashed using PBKDF2 with SHA-256 cryptographic salt.
- JWT tokens signed with HMAC-SHA256 using server-isolated `DJANGO_SECRET_KEY`.
- Cross-Site Scripting (XSS) mitigated through React JSX automatic string escaping.
- Cross-Site Request Forgery (CSRF) mitigated via Django CSRF middleware and token headers.

3.5.5 MAINTAINABILITY
- Modular architecture: decoupled `users`, `items`, `claims`, and `utils` Django apps.
- Strict TypeScript typing across all frontend service contracts and UI components.

3.5.6 PORTABILITY
- Works without modification across all standards-compliant modern web browsers.
- Fully deployable on standard cloud infrastructure (Vercel, Docker, AWS, Render).

3.7 DESIGN CONSTRAINTS
- Database engine strictly constrained to MongoDB NoSQL.
- Frontend strictly constrained to React 19 + TypeScript (no legacy class components).

3.9 OTHER REQUIREMENTS
- Accessibility: High contrast dark theme meeting WCAG 2.1 Level AA color standards.
